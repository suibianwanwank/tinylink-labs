# Reading concepts and building the linker

The theory chapters explain formats and algorithms; the class README specifies
the implementation task. Read the relevant theory section, then the current
README and its public types. The lab article introduces the goal and explains
the acceptance evidence. It is not a second copy of the specification.

All implementation and native acceptance work uses x86-64 Linux. Course examples
and tests supply their inputs; a path in an article must identify either a
provided repository file or a file generated by the accompanying commands.

## Current backend relationships

Classes0–8 build a common parsing, symbol, archive, reachability, and static-output
foundation. The advanced classes currently form these paths:

```text
                         class9 → class11 → class14  (static PIE, TLS, rustc)
                        /
classes0–8 foundation ──┼─ class10                    (ET_EXEC, merge, unwind)
                        \
                         class12 → class13           (ET_EXEC, debug, ICF)

class15 exercises these backend configurations; it is a validation harness.
```

Class11 separates its validated `Prepared` input from its `Lowered` PIE result.
The latter retains the layout, TLS template and load-time relocation records
before `Lowered::emit` serializes headers and startup descriptors. This is a
stage interface; it does not by itself combine the advanced paths above.

Class14 drops unwind annotations and keeps mergeable
constants as ordinary read-only storage; class13 does not inherit the PIE/TLS
backend. Read each README's supported subset before choosing a backend for an
input. PIE/TLS, unwind reconstruction, and debug/ICF use the separate output
paths shown above; an input requiring their combination has no supported
backend in these classes.

## Interpreting acceptance

Contract tests establish observable interface behavior: bounds, selection,
ordering, error values, and atomicity. Native tests establish behavior of the
listed generated programs and structural properties inspected by the tests.
Reference tests separately validate that the handout can be implemented. They
do not complete the student's TODOs or prove correctness for arbitrary inputs.

When a test fails, identify its input, the violated rule, and the coordinate of
the bad value. Use the smallest case before rerunning the whole suite. Never
weaken a provided test merely to accommodate a wrong implementation.
